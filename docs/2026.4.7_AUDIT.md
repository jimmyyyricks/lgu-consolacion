## Step 2 — Architectural Pattern in Use

**1. Layer vs Module organization:**
The project uses a **hybrid**: at the top level are both layers (`api/`, `application/`, `infrastructure/`, `domain/`) _and_ a separate `modules/` directory where each module owns its SQLAlchemy models, business APIs, and hooks. The generic `api/` routes serve all modules dynamically via metadata — no per-module router exists. This is closer to a **Frappe/ERPNext-style meta-driven architecture** than textbook Clean Architecture, but the structural intent is Clean Architecture with a generic API layer dispatching to module-specific hooks and business logic functions.

**2. Shared/core directories:**
Yes — `app/core/` (framework models, DB, security, seed), `app/services/` (16 cross-cutting services), `app/infrastructure/` (repositories, SMTP, JWT, SocketIO, cache) all act as fully shared cross-cutting tiers.

**3. Files that don't fit cleanly:**

- `app/services/scheduler.py` — imports directly from module-level `apis/` (breaks layer isolation)
- `app/core/display_names.py` vs `app/application/services/display_name_service.py` — duplicate responsibility with unclear authority
- `app/models/__init__.py` — convenience re-export that blurs where models live
- `app/routers/` — legacy API path coexisting with `app/api/` with no clear deprecation gate
- `app/epics/` — experimental code of unknown stability in production tree

**4. Actual top-level organizing principle:**
**Metadata-driven Modular Monolith with a Generic Protocol Layer.** The single set of generic routes (`entity_crud`, `entity_list`, etc.) dispatches to a metadata registry, which drives permissions, fields, workflows, and naming. Module-specific behavior is injected via a hook system and per-entity business API functions. This eliminates per-module routers but means the generic routes carry all cross-cutting orchestration responsibilities.

## Step 3 — Module Vertical Slices

### core_eam

- **Domain model**: `app/modules/core_eam/models/` — 27 auto-generated SQLAlchemy classes (Site, Department, Employee, Labor, Trade, Series, RequestActivityType, etc.). No business rule methods — pure data containers.
- **Schema**: Entity fields defined in `app/modules/core_eam/entities/*.json`. Runtime Pydantic schemas are generic (`ActionRequest`/`ActionResponse` in `app/schemas/base.py`), not per-entity.
- **Repository**: Generic `EntityRepository` in `app/infrastructure/database/repositories/entity_repository.py`. The `Series` model is specifically accessed by `app/services/naming.py` and `app/infrastructure/database/repositories/naming_repository.py`.
- **Service/Use Case**: `app/modules/core_eam/apis/` — validation and business functions for organizational entities.
- **Router**: Handled generically by `app/api/routes/entity_crud.py` — no dedicated core_eam router.
- **DI**: Routes inject `EntityRepository`, `RBACService`, `WorkflowService` via `Depends()` in `api/dependencies.py`.
- **Cross-module imports**: `Series` model imported by `app/services/naming.py` (cross-cutting — acceptable); `RequestActivityType` imported by `app/services/query_link_handlers.py` (minor coupling).

### purchasing_stores

- **Domain model**: `app/modules/purchasing_stores/models/` — 32 SQLAlchemy models (PurchaseRequest, PurchaseOrder, PurchaseReceipt, Item, Inventory, StockCount, Transfer, Vendor, etc.)
- **Schema**: JSON definitions in `entities/`. Generic request/response Pydantic contracts in `app/schemas/base.py`.
- **Repository**: Generic `EntityRepository`. No purchasing-specific repository.
- **Service/Use Case**: `app/modules/purchasing_stores/apis/` — 11 files: `purchase_order.py` (`create_po_from_pr`, `create_po_from_rfq`), `purchase_request.py` (approval validation), `purchase_receipt.py` (goods receipt + stock posting), `item_issue.py`, `item_return.py`, `stock_count.py`, `inventory_adjustment.py`, `transfer.py`, `transfer_receipt.py`, `inventory_low_stock_notification.py`
- **Router**: Generic `entity_crud.py`; workflow transitions via `workflow_router.py` inside module.
- **DI**: Via generic `api/dependencies.py` + hook_registry subscriptions in `hooks.py`.
- **Cross-module imports**: None outbound to other modules' internals. Inbound: `scheduler.py` imports `inventory_low_stock_notification`.

### asset_management

- **Domain model**: `app/modules/asset_management/models/` — 21 models (Asset, Equipment, Location, Position, AssetClass, Incident, Breakdown, Disposed, etc.)
- **Schema**: JSON `entities/`.
- **Repository**: Generic `EntityRepository`.
- **Service/Use Case**: `app/modules/asset_management/apis/` — `asset.py` (status transitions, validate), `asset_class.py`, `asset_position.py`, `equipment_schedule.py`, `breakdown.py`, `disposed.py`.
- **Router**: Generic `entity_crud.py`.
- **Cross-module imports**: Logically depends on `core_eam` (site/department/employee) and `work_mgmt` (incident → work order) — these dependencies are expressed through `document.get_doc()` calls on named entity strings, not direct model imports. This is the metadata facade pattern working correctly.

### maintenance_mgmt

- **Domain model**: `app/modules/maintenance_mgmt/models/` — auto-generated (MaintenanceRequest, MaintenanceOrder, MaintenanceCalendar, MaintenanceCondition, MaintenanceInterval).
- **Schema**: JSON `entities/`.
- **Repository**: Generic `EntityRepository`.
- **Service/Use Case**: `apis/` — 7 files including `maintenance_calendar.py`, `maintenance_condition.py`, `maintenance_interval.py` (APScheduler jobs), `maintenance_request.py`, `maintenance_order.py`, `maintenance_job_common.py` (shared utilities).
- **Router**: Generic routes + hooks.
- **Cross-module imports**: Inbound from `scheduler.py` (imports scheduled job functions). Outbound dependencies expressed via document facade.
- **Concern**: `scheduler.py` (a shared service) imports directly from `maintenance_mgmt.apis.*` and `purchasing_stores.apis.*`. This is a layering violation — a shared service should not reach into a module's application tier.

### work_mgmt

- **Domain model**: `app/modules/work_mgmt/models/` — 15 models (WorkOrder, WorkOrderActivity, WorkOrderLabor, WorkOrderParts, etc.)
- **Schema**: JSON `entities/`.
- **Repository**: Generic `EntityRepository`.
- **Service/Use Case**: `apis/` — 8 files: `work_order.py`, `work_order_activity.py`, `work_order_labor.py`, `work_order_equipment_assignment.py`, `work_order_parts.py`, `work_order_checklist.py`, `work_order_labor_assignment.py`, `work_order_activity_actions.py`.
- **Router**: Generic routes; `workflow_router.py` in module for WO state machine.
- **DI**: Hook registrations in `hooks.py`; server actions registered via `@server_actions.register(...)` decorator.
- **Cross-module imports**: None direct; cross-module data via document facade.

## Step 4 — Clean Architecture Compliance Audit

### Domain Layer

| Rule                                          | Status        | Evidence                                                                                                                                                                                                            |
| --------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain models are pure Python / no SQLAlchemy | **VIOLATION** | All "domain" models are SQLAlchemy ORM classes. There are no separate plain-Python domain objects. `app/core/framework/models/auth.py`, `app/modules/*/models/*.py` all use `Column`, `relationship`, `ForeignKey`. |
| Business rules enforced in domain methods     | **VIOLATION** | No business rule methods exist on any model class. All validation and invariant checking lives in `apis/` functions or hooks.                                                                                       |
| Domain models have zero infra imports         | **VIOLATION** | Every model file imports `from sqlalchemy import Column, Integer, String, ForeignKey` and `from app.core.base_model import BaseModel`.                                                                              |

**Assessment:** This project does not implement a Domain layer in the Clean Architecture sense. There are no domain entities — only ORM models. The `app/domain/protocols/` directory declares abstract interfaces, which is the correct intent, but the concrete data carrier is always the SQLAlchemy model.

### Application Layer

| Rule                                                 | Status                | Evidence                                                                                                                                                                                                                   |
| ---------------------------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Services only import from domain and repo interfaces | **PARTIAL VIOLATION** | `app/services/document_mutation.py` works through `EntityRepository` (good), but `app/services/naming.py` imports `Series` SQLAlchemy model directly. `RBACService` imports `User`, `Role`, `EntityPermission` ORM models. |
| Services do NOT import SQLAlchemy models directly    | **VIOLATION**         | `naming.py` line ~46: `from app.modules.core_eam.models.series import Series`; `rbac.py`: `from app.core.framework.models.auth import User, Role, EntityPermission`                                                        |
| Services do NOT import FastAPI                       | **PASS**              | No `from fastapi import` found in any `services/` or `application/services/` file.                                                                                                                                         |
| Business logic not duplicated in routers             | **PARTIAL VIOLATION** | `entity_list.py` contains 150+ lines of link title resolution and batch query building that should be in a service. `entity_crud.py` contains `_validate_required_fields()` and `_coerce_incoming_types()` inline.         |
| Services not aware of HTTP concerns                  | **PASS**              | Services return plain dicts or model objects, not `Response` objects.                                                                                                                                                      |

### Infrastructure Layer

| Rule                                                      | Status        | Evidence                                                                                                                                                                                                                                            |
| --------------------------------------------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repositories implement an interface from domain           | **PARTIAL**   | `app/domain/protocols/` declares abstract contracts. `EntityRepository` appears to conform, but compliance is not enforced by Python (no `class EntityRepository(EntityRepositoryProtocol)` inheritance found — unclear without reading all files). |
| Repositories are the ONLY place SQLAlchemy queries appear | **VIOLATION** | `entity_list.py` (router) executes direct SQLAlchemy select queries. `entity_crud.py` contains `await db.execute(select(model).where(...))`. `naming.py` (service) queries the `Series` model directly.                                             |
| No raw SQL outside repository files                       | **VIOLATION** | Direct `select()` calls appear in multiple route handlers and the naming service.                                                                                                                                                                   |

### API Layer

| Rule                                              | Status        | Evidence                                                                                                                                                                                                                          |
| ------------------------------------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Routers contain NO business logic                 | **VIOLATION** | `entity_list.py` (~150+ lines): contains `_build_link_titles_batch()` — a complex query and resolution function. `entity_crud.py`: contains `_validate_required_fields()`, `_coerce_incoming_types()`, inline `select()` queries. |
| Routers only call service methods                 | **PARTIAL**   | The main happy path calls `entity_service.*` correctly, but supplemental logic is inlined.                                                                                                                                        |
| Routers do NOT call repositories directly         | **VIOLATION** | `entity_crud.py` line ~208: `result = await db.execute(select(model).where(model.id == request.id))` — direct ORM call in route.                                                                                                  |
| Routers do NOT instantiate domain models directly | **PASS**      | No `MyModel(...)` in route files; creation is through services.                                                                                                                                                                   |

### Dependency Injection

| Rule                                                 | Status           | Evidence                                                                                                                                                 |
| ---------------------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Services injected via FastAPI Depends()              | **PASS**         | `api/dependencies.py` provides proper `Depends()` factories for all services.                                                                            |
| Repositories injected into services                  | **PASS**         | Repo → Service injection chain in `dependencies.py`.                                                                                                     |
| No service/repo instantiated inline in route handler | **PARTIAL PASS** | Main services are injected. However, utility helpers like `NamingService`, `SocketIOManager` are called as module-level singletons rather than injected. |

### 5. Missing Abstraction (No Repository Interface Enforcement)

**`app/infrastructure/database/repositories/entity_repository.py`**  
The `EntityRepository` is generic and handles all entities, but the `app/domain/protocols/` interfaces are not enforced via Python inheritance. If a developer bypasses the repo and calls `db.execute(select(...))` directly (as seen in route handlers), there is no compile-time or type-check barrier.
_Fix:_ Annotate `EntityRepository(EntityRepositoryProtocol)` and enable mypy strict checks on the routing layer to block direct `db.*` usage.

### 6. Frappe-style Collapsing

**`app/modules/*/apis/*.py` (all module API functions)**  
Each API function (e.g. `create_po_from_pr()`) acts simultaneously as: a validator, a domain logic executor, a document writer (via `new_doc`/`save_doc`), and a side-effect trigger (email, SocketIO). This is the Frappe-style function pattern.

Example — `app/modules/purchasing_stores/apis/purchase_order.py`:

```python
async def create_po_from_pr(doc, db, user):
    # Validation (business rule)
    if doc.workflow_state != "approved": raise ...

    # Domain logic (grouping lines by vendor)
    vendor_groups = defaultdict(list)
    for line in pr_lines:
        vendor_groups[line.vendor].append(line)

    # Infrastructure write
    po = await new_doc("purchase_order", db, ...)
    await save_doc(po, db, commit=False)

    # Side effect
    await emit_created("purchase_order", ...)
```

_Anti-pattern:_ Validation + domain logic + DB write + side effect in one function. Not directly harmful given the document facade abstraction, but makes unit testing without a DB session difficult.\
_Fix:_ Extract validation into `PurchaseOrderValidator`, logic into a pure function, keep the orchestration function as a thin coordinator. This is a medium-priority refactor.

## Step 8 — Final Report

### 8A. Architecture Summary

This backend implements a **Metadata-Driven Modular Monolith** with partial Clean Architecture layering. The organizing principle is not Clean Architecture's concentric-ring model nor a conventional modular monolith — it is a **Frappe/ERPNext-inspired framework** where entity definitions (JSON) drive model generation, a generic API layer dispatches to a metadata registry, and per-module behavior is injected through hooks and business API functions. This is a deliberate, coherent design choice for an ERP-class system and it is largely consistent across the codebase.

Where the design breaks down is in the absence of a true domain layer (ORM models serve as domain objects), the blurring of the service/repository boundary in shared services (`naming.py`, `rbac.py` do their own ORM queries instead of delegating to repos), and two specific anti-patterns: a shared service (`scheduler.py`) that is directly coupled to module-level application code, and route handlers (`entity_list.py`, `entity_crud.py`) that contain 100–150 lines of query logic that belongs in the service tier. The legacy `routers/` path coexisting with the new `api/` path is a maintenance liability but does not introduce logical inconsistency.

### 8D. What Is Working Well

1. **Generic metadata-driven API layer.** A single set of route handlers (`entity_crud`, `entity_list`, `entity_workflow`, etc.) serves 100+ entities via metadata — no per-entity router proliferation. This is the right architectural choice for an ERP system and is executed consistently.

2. **Module self-containment.** Each of the five domain modules owns its models, entities, business APIs, and hooks. No module imports from another module's internals. Cross-module data flows through the document facade only.

3. **Hook system for lifecycle separation.** `@hook_registry.before_save`, `@hook_registry.after_save`, and `@hook_registry.workflow` cleanly separate side effects (email, derived field computation, stock posting) from the core save path. Modules extend behavior without modifying shared code.

4. **Generic `EntityRepository`.** The single `entity_repository.py` that operates on any entity by `__tablename__` lookup is correct infrastructure abstraction. It prevents entity-specific SQL from spreading across the codebase.

5. **Proper Dependency Injection.** `api/dependencies.py` provides `Depends()` factories for all repositories and services. Routes receive injected dependencies, not module-level singletons (for the primary service path).

6. **Workflow as data, not code.** Workflow states, actions, and transitions are stored in the database and read via `WorkflowService`. No if/else state machines hard-coded in business logic.

7. **Server Actions registry.** Custom operations are registered via `@server_actions.register(entity, action_name)` decorator, keeping the dispatch mechanism open/closed — adding a new action doesn't require modifying any route or shared file.

8. **Async throughout.** The entire stack uses `async/await` with `AsyncSession`, enabling non-blocking I/O under load without thread pool pressure.

9. **Module load ordering.** `core/loader.py` loads modules in declared dependency order, preventing circular import issues at startup.

10. **No circular dependencies detected.** All 30 cross-module imports found are unidirectional. This is a significant achievement in a 382-file codebase.
