# Epic: One-Command Install Wizard

**Status:** In Progress — Admin always created at CLI; browser lands on `/login`  
**Priority:** Critical — Production rollout scheduled within 1 week  
**Last Updated:** 2026-04-13

---

## 1. Goal

Deliver a single `./install.sh` command that:

1. Prompts for all credentials upfront (PostgreSQL superuser + administrator account)
2. Installs all backend Python dependencies into a virtualenv
3. Installs all frontend Node dependencies via pnpm and builds for production
4. Creates the PostgreSQL database and app role with auto-generated UUID-based names
5. Creates all database tables (SQLAlchemy `create_all`)
6. Seeds all reference data (roles, permissions, workflow states, workflow actions, workflows, request activity types)
7. Creates the administrator account from the credentials typed at the CLI
8. When the user opens the browser, they land on **`/login`** — not a setup wizard

`/setup` is kept as a manual fallback only (accessible directly by URL). The Frappe model is adopted fully: admin is always created at install time, there are no hardcoded defaults, and no `.env.example` copy step.

---

## 2. How Frappe Does It (Reference Model)

Frappe uses a CLI tool called **bench**. Their install flow is:

```bash
bench init frappe-bench          # creates virtualenv, installs frappe, builds assets
cd frappe-bench
bench new-site mysite \
  --db-root-username root \
  --db-root-password <MYSQL_ROOT_PASS> \
  --admin-password <ADMIN_PASS>  # creates DB, creates tables, seeds, creates admin
bench start                      # starts all processes
```

**Key design decisions Frappe makes:**

| Decision              | Frappe Approach                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| Database creation     | Requires explicit `--db-root-username/password` (a privileged DB user). Never guesses.                       |
| Admin creation        | Done at install time via `--admin-password`. Not deferred to a web wizard.                                   |
| Config file           | Each site gets a `site_config.json` auto-generated by `bench new-site`. No manual copying of `.env.example`. |
| Setup wizard          | Frappe's web wizard is for **company/org configuration**, not admin creation. Admin always exists from CLI.  |
| No hardcoded defaults | There are no default passwords anywhere in source. All secrets passed as CLI args.                           |

**What EAM should adopt from Frappe:**

- Always require an explicit privileged DB connection string for install (not clever fallbacks)
- Auto-generate the `.env` from install args, not from a static `.env.example` copy
- The web `/setup` wizard should be a **company/org setup** step, not the admin creation step (or admin creation must be bulletproof from CLI)

## 3. Revised Design (2026-04-12) — UUID DB + Interactive CLI Prompts

### Problem with the previous approach

The previous design copied `.env.example` to `backend/.env` with hardcoded defaults (`eam_dev` / `eam_local_dev`). This meant:

- Every install on every machine used the same predictable database name and role.
- Production deployments required manual `.env` editing after install.
- No single-command path to a unique, isolated database per installation.

### New install model

Inspired by how tools like Frappe generate random DB credentials and write them to a site config file, `install.sh` now:

1. **Generates unique credentials at install time** using OS tools:
   - `SITE_ID` — 12-char hex (from `openssl rand -hex 6`), e.g. `a3f7c2e1b908`
   - `DB_NAME` / `DB_ROLE` — `eam_<SITE_ID>`, e.g. `eam_a3f7c2e1b908`
   - `DB_PASSWORD` — 32-char random string (from `openssl rand -base64 32`)
   - `SECRET_KEY` — 64-char random string (from `openssl rand -base64 48`)

2. **Prompts interactively** for PostgreSQL superuser credentials (needed to `CREATE ROLE` and `CREATE DATABASE`). Defaults to OS peer auth (`postgresql:///postgres`) if password is left blank.

3. **Writes `backend/.env` from generated values** — not a static copy of `.env.example`. The written file contains the real, unique credentials for this installation.

4. **Always prompts for the administrator account** at the CLI (before deps install) — credentials are passed explicitly to `setup_system.py`. The browser-based `/setup` wizard is kept as a manual fallback URL only.

### Install flow

```
./install.sh
      │
      ├─ [PG prompt] Superuser host / port / user / password
      │               → DATABASE_BOOTSTRAP_URL set in shell env
      │
      ├─ [Admin prompt] Username / Email / Full name / Password (confirmed)
      │               → ADMIN_* variables set in shell env
      │               (all prompts before install — user walks away while deps install)
      │
      ├─ [0] generate_site_credentials() — only if backend/.env missing
      │       SITE_ID   = openssl rand -hex 6        → e.g. a3f7c2e1b908
      │       DB_NAME   = eam_<SITE_ID>
      │       DB_ROLE   = eam_<SITE_ID>
      │       DB_PASS   = openssl rand -base64 32
      │       SECRET_KEY = openssl rand -base64 48
      │       → backend/.env written with real generated values
      │
      ├─ [1] install_backend()
      │       python3 -m venv .venv
      │       pip install -r requirements.txt
      │
      ├─ [2] install_frontend()
      │       pnpm install
      │       pnpm build → frontend/.output/
      │
      └─ [3] python scripts/setup_system.py --all \
                      --admin-username <USERNAME> \
                      --admin-email <EMAIL> \
                      --admin-full-name <FULL_NAME> \
                      --admin-password <PASSWORD>
                      ├─ CREATE ROLE eam_a3f7c2e1b908
                      ├─ CREATE DATABASE eam_a3f7c2e1b908
                      ├─ init_db()       → CREATE TABLE
                      ├─ run_all_seeds() → 6 idempotent seeders
                      └─ create_superadmin() — always created

Browser: GET / → unauthenticated → /login  (no /setup redirect)
```

### Re-runs (idempotent)

- If `backend/.env` already exists, `install.sh` skips credential generation and uses the existing file.
- All seed steps are idempotent (skip on conflict).
- DB/role creation is skipped if they already exist.

### Seed Pipeline (6 seeders, idempotent)

```
roles → entity_permissions → workflow_states → workflow_actions → workflows → request_activity_types
```

No domain data seeded. All module entities (assets, work orders, etc.) are created via the application, not seeded.

### Install Invocation

```bash
# Standard — prompts for PG superuser + admin account interactively:
./install.sh

# CI/automation only (skips admin creation — not recommended for production):
./install.sh --skip-admin

# Pre-supply PG bootstrap URL to skip that prompt:
DATABASE_BOOTSTRAP_URL=postgresql:///postgres ./install.sh

# Speed up re-test by skipping frontend build:
./install.sh --skip-frontend-build
```

## 4. Test Run Results (2026-04-12)

Three clean-clone install attempts were made. Issues discovered and fixed in sequence:

### Attempt 1 — Failure: `pnpm --frozen-lockfile` rejected

**Root cause:** `pnpm-lock.yaml` was stale (5 new packages in `package.json` not in lockfile).

**Fix applied:**

- Removed `--frozen-lockfile` from `install.sh` → uses plain `pnpm install`
- Regenerated `pnpm-lock.yaml`

---

### Attempt 2 — Failure: `InsufficientPrivilege` on DB bootstrap

**Root cause:** The bootstrap URL derivation used the app user's URL (`eam_dev`) pointing to `postgres` DB. The `eam_dev` role exists but has no `CREATEROLE`/`CREATEDB` privilege, so `CREATE ROLE` raises `InsufficientPrivilege`.

**Fix applied:** Wrapped in `except psycopg2.errors.InsufficientPrivilege` — gracefully skips and continues.

**New problem revealed:** After skip, `init_db()` connects to `eam_local_dev` which already exists (dev DB) — so tables were created there. **This masked the real issue: the install ran against an existing dev DB, not a fresh one.**

## 7. Architecture Diagram (Final Install Flow)

```
./install.sh
      │
      ├─ [collect upfront — user walks away after this]
      │   ├─ PG prompt: host / port / user / password → DATABASE_BOOTSTRAP_URL
      │   └─ Admin prompt: username / email / full name / password (confirmed)
      │
      ├─ [0] generate_site_credentials() — only if backend/.env missing
      │       SITE_ID    = openssl rand -hex 6      → e.g. a3f7c2e1b908
      │       DB_NAME    = eam_<SITE_ID>
      │       DB_ROLE    = eam_<SITE_ID>
      │       DB_PASS    = openssl rand -base64 32
      │       SECRET_KEY = openssl rand -base64 48
      │       → write_backend_env() → backend/.env
      │       → ensure_frontend_env() → frontend/.env
      │
      ├─ [1] install_backend()    python3 -m venv .venv && pip install -r requirements.txt
      ├─ [2] install_frontend()   pnpm install && pnpm build → frontend/.output/
      │
      └─ [3] python scripts/setup_system.py --all \
                  --admin-username ADMIN_USERNAME \
                  --admin-email    ADMIN_EMAIL \
                  --admin-full-name ADMIN_FULL_NAME \
                  --admin-password  ADMIN_PASSWORD
              ├─ CREATE ROLE  eam_<SITE_ID> WITH LOGIN PASSWORD '...'
              ├─ CREATE DATABASE eam_<SITE_ID> OWNER eam_<SITE_ID>
              ├─ init_db()       → CREATE TABLE (SQLAlchemy)
              ├─ run_all_seeds() → 6 idempotent seeders
              └─ create_superadmin() → administrator account always created

Browser: GET / → unauthenticated → /login
         /setup reachable directly as manual fallback (no auto-redirect)
```
